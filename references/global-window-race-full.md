# Free Mint Global Window Race (full detail)

## Free Mint with Global Window Cap (bot race pattern)

Some mints are "free, 1 per N seconds" but the slot is **GLOBAL** (all minters compete for the same single slot per window), not per-wallet. Rentoids (Robinhood, `OnChainLandlord.sol`) is the worked example: `FREE_PER_BLOCK=1`, `FREE_WINDOW=5s`, `WALLET_LIMIT=50`, `MAX_PER_TX=10`, paid lane `0.002 ETH` skips the cap.

**Hard reality from a live run (175 attempts):**
- Win rate ≈ **3%** (5 mints / ~175 txs) — dozens of bots race each 5s window
- Each miss still burns a nonce + gas (tiny on Robinhood, but nonce count balloons)
- One wallet caps at 50 → "loop until supply out" is IMPOSSIBLE from one wallet (10k supply / 50 cap = need 200 wallets)
- Mint rate observed: ~1 per 5-10 min as competition heats up, worse as supply thins

**Working loop pattern (see `scripts/free-mint-race-loop.js`):**
1. Before sending: check `mintsPerWallet(wallet)` (cap), `nextTokenId()` (sold out), and **`staticCall` the mint** to see the exact revert reason (e.g. "Free slots full this block") without burning a tx
2. Send with `nonce: getTransactionCount(wallet, "pending")` — sequential, no replacement errors
3. On revert: classify reason (slot-full → wait window; sold-out → stop; wallet-limit → stop)
4. Sleep the window interval between attempts; shorter retry (2s) after a revert
5. Gas: hardcode `maxFeePerGas 0.15 gwei / maxPriorityFeePerGas 0.01 gwei / type 2` on Robinhood (see pitfall 11 in meme-trade-ops — never trust `getFeeData()` there)

**Racing optimization — Pre-Sign & Fire (beat the naive loop):**
The naive loop above costs 3-4 RPC round-trips per attempt (mintsPerWallet + getTransactionCount + estimate + send). On a global-window race that's 200-400ms of overhead. When the operator asks to actually compete, switch to pre-sign & fire:

```
1. mint(1) calldata is CONSTANT → sign the tx ONCE per nonce, offline, 0 RPC
2. Wait for the window boundary (timestamp % FREE_WINDOW == 0)
3. Fire eth_sendRawTransaction at the boundary → 1 RPC per attempt
4. Success or revert both consume the nonce → presign nonce+1, repeat
```

- Result: ~50-100ms total overhead instead of 300-400ms. Still loses to US-East bots (~150-300ms physical latency gap) — be honest: this closes the code gap, not the geography gap.
- Optional `--lead` mode: fire a few ms BEFORE the boundary so the tx sits in the sequencer queue and executes right as the window flips. Can steal a slot when the dominant bot stumbles.
- **Pitfall: hammering 2× rate eventually trips RPC rate limits** — a 1.2s retry loop ran ~10 min then got `403 forbidden` from `rpc.mainnet.chain.robinhood.com`. Throttle to window-aligned fires, not max-rate spam.

**Decision framework:** if the operator wants quantity fast and the project has a paid lane, paid is the only deterministic path. Free lane = patience + near-zero cost, but treat it as "eventually some" not "all of them".

- **⚠️ REACTIVE TRIGGERS LOSE 1-SLOT RACES — proactive timing only (Merge Cats v6 lesson):** polling `nextWindowIn()`/`currentWindow()` and arming the fire on the detected change adds an RPC round-trip (80-160ms) of latency BEFORE every fire — against bots firing on local clock at boundary-165ms you lose 100% of slots. v6 (signal-triggered) climbed on-chain silently while the log showed 0 wins; v7 (proactive wall-clock + dynamic period) is the form that competes. The ONLY exception: when the boundary is NOT computable from a public getter, reactive is the fallback.
- **⚠️ Verify wins on-chain, not just receipts (Merge Cats silent-win bug):** with fast-changing windows, receipts can arrive after the pending-drop timeout (~1.5-2s) → the win is consumed but never logged, the watchdog never fires, and the operator thinks the race is dead while balanceOf climbs. Fix: on pending-drop, call `balanceOf(wallet)` — if it exceeds the tracked minted count, log the difference as wins. Receipts are a fast-path signal, not the source of truth.
- **⚠️ balanceOf null ≠ 0 (Merge Cats footgun):** `Number(null) === 0` — a failed balance read silently turns a 10/10 wallet into "0/10", causing needless fires and potential double-mint. If the balance read returns null, SKIP the wallet ("balance gagal dibaca — SKIP"), never assume 0.
- **⚠️ Diagnostic before tuning: nonce progression tells landing-vs-stuck (Merge Cats):** `getTransactionCount(wallet,'latest')` > start nonce = txs ARE landing → you're losing the slot race (timing/competition problem — do NOT keep revising the script); equal = txs stuck (broadcast/RPC/nonce problem — fix infra). Evidence: nonce 399→432 (33 txs landed) with 0 wins = competition, not script.
- **⚠️ Free-lane global cap: probe `freeMinted()` / `freeCap()` (Merge Cats):** a free lane can be exhausted (freeMinted >= freeCap) while totalSupply still has room — "kenapa kita ga dapet lagi" may be answered by "the lane is done", not "script broken". Delta of `totalSupply() - freeMinted()` = paid-lane usage; a big jump means whales are buying through and competition hardened.
- **⚠️ Competition-hardening stop rule (operator frustration, Merge Cats 2026-08):** when supply jumps thousands in minutes (2,624 → 7,624) and wins go to 0% over hundreds of attempts, the play is structurally lost — early wins (46x) came from starting at low supply; late entry into a hardened 1-slot-global lane wins nothing. - **⚠️ DRY SPELL ≠ BROKEN — diagnose BEFORE killing a running race (Merge Cats 2026-08, the exact mistake):** a 5-10 min stretch with no wins in a 1-slot-GLOBAL windowed race is NORMAL (dozens of bots compete per window; wins arrive in bursts). In this session a healthy v1 (already 42 wins, still winning) was killed during a ~6-min dry spell and replaced with untested rewrites — the result was ~12 min of 0 wins from broken scripts while the ORIGINAL process kept winning in the background. Before killing/rewriting a running race, run the diagnostic checklist (full recipe: `references/dynamic-window-free-mint-race.md`): (1) process alive? (`ps aux | grep`); (2) is `totalSupply()` still rising? — rising = race alive, OTHER agents winning, your timing is the issue; (3) re-read `freeWindow()`/`nextWindowIn()` — did the duration change? (4) check win-rate history in the log for past dry-spell lengths before concluding anything. Only kill + rewrite after a MECHANICAL diagnosis (window changed, RPC dead, nonce stuck), never on a dry spell alone. Cheap verification first: `nextWindowIn()` sampled over 2 cycles tells you the real boundary in seconds.
- **Nonce collision on race restart (Merge Cats v5 2026-08):** after killing a race instance, its already-broadcast txs can still sit pending in the mempool holding the nonces. A new instance reading `getTransactionCount(addr, 'pending')` then signing the SAME nonce gets rejected by every RPC (`already known` / `nonce too low` / `replacement transaction underpriced`) — looks like "broadcast failed" but is actually a nonce collision. Fix (in v6): on broadcast error, match the message; if it's a nonce-taken variant → re-read the nonce and continue, do NOT count it as a failure. Also sync `balanceOf` from on-chain at startup so a mid-race restart continues from the real count instead of double-minting toward a stale cap.

- **⚠️ WINDOW CAN SHRINK TO 1s — countdown signals go DEGENERATE (Merge Cats 2026-08, same session):** the operator reported the site dropping to "1 sec per 1 NFT" (`freeWindow()==1`). At 1s, `nextWindowIn()` is ALWAYS 1 and `currentWindow()` stays frozen at 1 — the `2→1` transition trigger NEVER fires, so a v6 that only watches `nextWindowIn()` goes 0 fires silently. Fix (in v6 final): make **`currentWindow()` increments the PRIMARY trigger** — when `currentWindow()` ticks up, a new window just opened; arm the fire `periodMs - LEAD` before the NEXT expected tick (`periodMs = freeWindow()*1000`, re-read every 5s not 30s so the estimate stays fresh through mid-race flips). This works for ANY duration including 1s (2s/24s/0s edge observed too). Keep the nwi==1 logic as fallback only for durations >1s. Also: at sub-5s windows the old 30s `freeWindow()` re-read interval is too slow — drop it to 5s so `🔁 WINDOW BERUBAH` logging and period estimates track the flips.
- **⚠️ BROADCAST MUST BE FAN-OUT PARALLEL, never sequential (Merge Cats v5/v6 regression, 2026-08):** a "try RPC 1, then RPC 2, then RPC 3" sequential broadcast eats up to 900ms PER WALLET when the first RPC is slow — on a 1-slot-global race that loses EVERY window (all txs land, all revert, nonce still burns). The proven v1 pattern that won 46x is `Promise.allSettled` fan-out: send the SAME pre-signed tx to all RPCs simultaneously, take the first success, ~700ms overall timeout. If a mid-session rewrite ever switches broadcast to sequential "for cleanliness", that is a race-losing bug — revert to fan-out.
- **⚠️ `Number(null) = 0` balanceOf bug (Merge Cats v6, 2026-08):** when a startup `balanceOf()` RPC read fails, `callRpc` returns `null`, and `Number(null)` silently becomes `0` → a FULL wallet (10/10) reads as "0/10 → eligible" → the script re-fires from it, burning nonces on guaranteed cap-reverts (and if the operator SOLD those NFTs, balance really is 0 and the wallet genuinely re-mints — see operator-sale bullet below). Fix: null-check the balance read and SKIP the wallet on read failure (`if (minted === null) { skip }`) — never coerce null to 0.
- **⚠️ OPERATOR CAN SELL MID-RACE — balances drop to 0 and wallets look eligible again (Merge Cats 2026-08):** the operator sold wallet 1+2's cats for ~$40 mid-race; on-chain `balanceOf` dropped to 0, so the next restart read them as "0/10, mint more" and re-fired from them. When the operator reports a sale / balance drop, EXCLUDE those wallets from `TARGET_WALLETS` explicitly (the script cannot know the operator sold — 0 balance is indistinguishable from "not minted yet"). Also the "race stuck" alarm earlier in the session was triggered by exactly this: balances read 0 on 3 RPCs → looked like a catastrophic bug → it was just the operator selling. Check with the operator before panicking about disappearing balances.
- **⚠️ WIN LOGGING MISSES AT FAST WINDOWS — verify via balanceOf (Merge Cats v6, 2026-08):** at 1-2s windows, receipt checks (400ms timeout, miss≥3 drop) can miss a WIN that actually landed — the NFT mints on-chain but the log shows no `🎉 WIN` and reports say "0 wins". Symptom: `totalSupply()`/`balanceOf` keeps rising while the log shows nothing. Fix (in v6): when a pending tx is dropped after missed receipts, re-read `balanceOf` — if it increased, log the WIN via balance (`🎉 wallet X: WIN xN via balance`) and update the counter. Rule of thumb for fast-window races: TRUST ON-CHAIN BALANCES over the win log; a "0 wins in log" at 1s windows may still be +5 on-chain.
